# tapprobe — зонд маршрутизации

Отвечает на один вопрос, от которого зависит вся архитектура агентской части:

> Уводит ли Windows трафик, привязанный к source-адресу `192.168.N.100`,
> в TAP-адаптер, которому этот адрес принадлежит?

Windows выбирает интерфейс **по адресу назначения**, а не по источнику, и по
умолчанию работает в режиме weak host send — пакет с чужим source спокойно
уходит через физическую сетевую. Но у route selection есть нюансы вокруг явного
`bind()`, и цена ошибки здесь — недели работы. Поэтому проверяем экспериментом.

| Результат | Что означает | Объём работ |
|---|---|---|
| **Пакеты появились** | перехват не нужен | TAP + lwIP + посредник Host, ~2 недели |
| **Не появились** | нужен WinDivert для увода по source | то же + драйвер-перехватчик, ~месяц |

Заодно проверяется вторая гипотеза: **опознает ли твой софт такой адаптер как
воткнутый USB-модем**, если подменить описание и MAC.

---

## Подготовка

### 1. Драйвер

Нужен tap-windows6 от OpenVPN — настоящий Ethernet-адаптер с MAC и ARP.
Wintun не подходит: он регистрируется как `NdisMediumIP` с
`IfType = IF_TYPE_PROP_VIRTUAL` и модемом выглядеть не может в принципе.

```
https://build.openvpn.net/downloads/releases/tap-windows-9.24.7-I601-Win10.exe
```

Поставить обычным двойным кликом. Создастся один адаптер.

### 2. Проверить, что видно

**Все команды ниже — из терминала, запущенного от администратора.**

```
tapprobe list
```

Должен показать адаптер с описанием `TAP-Windows Adapter V9`.

---

## Тест

### Шаг 1 — настроить адаптер как модем 55

```
tapprobe create 55
```

Даёт адаптеру `192.168.55.100/24`, шлюз `192.168.55.1`, DNS `192.168.55.1`
и переименовывает подключение в `modem55`.

> **Не бери N, совпадающий с твоей реальной сетью.** Если компьютер живёт в
> `192.168.1.0/24`, то `tapprobe create 1` создаст вторую маршрутку на тот же
> префикс и машина потеряет связь со своей же LAN. Эти грабли уже собраны в
> Linux-версии — там их ловит `ns_conflict()`.

### Шаг 2 — замаскировать под USB-модем

```
tapprobe disguise 55
```

Пишет в реестр описание `Remote NDIS based Internet Sharing Device` и MAC с
OUI Huawei (`00:1E:10`). Подпись драйвера при этом не ломается — она покрывает
файлы пакета, а не реестр.

Чтобы изменения вступили в силу, адаптер надо передёрнуть:

```
netsh interface set interface name="modem55" admin=disable
```

```
netsh interface set interface name="modem55" admin=enable
```

Теперь посмотри в диспетчере устройств и **покажи адаптер своему софту** —
опознает как модем или нет.

### Шаг 3 — главный тест

В первом окне:

```
tapprobe listen 55
```

Он ждёт пакеты и печатает всё, что приходит. На ARP-запросы отвечает сам —
это обязательно, иначе Windows не выяснит MAC шлюза и не отправит вообще
ничего, а тест дал бы ложный отрицательный результат.

Во втором окне (тоже от администратора):

```
curl --interface 192.168.55.100 -m 5 http://1.1.1.1
```

`curl` завершится ошибкой — на той стороне туннеля пока никого нет. Это
нормально, смотреть надо в первое окно.

## Как читать результат

```
  ARP   кто такой 192.168.55.1?  -> отвечаю
  TCP   192.168.55.100:52341 -> 1.1.1.1:80   <<< ВНЕ ПОДСЕТИ — ЭТО ТО, ЧТО МЫ ИЩЕМ
```

**Строка с пометкой `ВНЕ ПОДСЕТИ` — это победа.** Значит Windows увела в TAP
трафик, привязанный к нашему source-адресу, и никакого перехватчика не нужно.

Если видно только ARP, а строк с внешними адресатами нет — Windows отправила
пакеты через физическую сетевую, и понадобится WinDivert.

Ничего не видно вообще, даже ARP — адаптер не поднялся: проверь права
администратора и что `tapprobe create 55` отработал без ошибок.

---

## Дополнительно стоит проверить

Пинг шлюза — должен вызвать ARP, а затем ICMP в окне зонда:

```
ping -n 2 192.168.55.1
```

И то, как выглядит адаптер для системы:

```
powershell "Get-NetAdapter | Select-Object Name,InterfaceDescription,MacAddress,ifType"
```

У настоящего USB-модема `ifType` = 6 (Ethernet). Должно совпасть.

## Уборка

```
netsh interface ip set address name="modem55" dhcp
```

Описание в реестре вернётся само при переустановке драйвера, либо правится
обратно на `TAP-Windows Adapter V9` в той же ветке.
